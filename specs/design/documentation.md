# 16 — User-Facing Documentation (a deliverable, not an afterthought)

Comprehensive, user-facing documentation is part of what it means to ship a full WYSIWYG +
source Markdown editor. Documentation is produced **as features are implemented** and
published automatically, so the docs always reflect the editor's real behavior.

## 16.1 Requirement

Every user-facing feature must ship, **in the same change that implements it**:

1. A **Markdown documentation page** under `docs/`, placed in the right category (Features /
   Editing / Reference), explaining what the feature is, how to use it (typed Markdown,
   toolbar, slash menu, shortcuts), and the Markdown it maps to.
2. A **screenshot** (for anything visual) under `docs/images/`, **generated from the real
   editor** — not hand-drawn or stale.
3. **Cross-links** to related topics (categories ↔ topics ↔ subtopics), so the docs form a
   navigable web, not isolated pages.

A feature is not "done" (see [10-testing-ci-packaging.md](./testing-ci-packaging.md) §10.6)
until its docs page + screenshot exist and the navigation links it in.

## 16.2 The docs system

- **Source:** plain Markdown in `docs/` (so the editor's own output format documents the
  editor). Site nav/theme in `mkdocs.yml`.
- **Renderer:** **MkDocs (Material theme)** turns `docs/` + images + cross-links into a static
  site. Chosen because it renders Markdown with images and inter-page links directly, supports
  nested nav (categories → topics → subtopics), search, and code copy.
- **Screenshots:** generated by `test/docs/generate_screenshots_test.dart` — a widget test that
  loads real fonts, drives each feature through the actual `MarkdownEditor`, and writes PNGs
  to `docs/images/`. Run with `flutter test test/docs/generate_screenshots_test.dart`. Adding
  a visual feature means adding a capture case there.
- **Publishing:** `.github/workflows/docs.yml` regenerates screenshots, builds the site with
  `mkdocs build --strict`, and deploys to **GitHub Pages** on every push to the default
  branch. So adding a feature (with its docs) automatically updates the hosted documentation.

## 16.3 Why generate screenshots from the editor

Hand-managed screenshots rot. By capturing them from the real widget in a test:

- They can never drift from actual behavior (a UI change shows up in the next build).
- `--strict` builds fail if a referenced image or link is missing, catching doc gaps in CI.
- The same harness that proves the UI works (golden-style capture) produces the docs imagery.

## 16.4 Coverage of the docs

The docs must comprehensively cover the editor's capabilities — every block type, every inline
mark, every input rule, the slash menu, source mode, keyboard shortcuts, undo/redo, and
(as they land) tables, diagrams, collaboration, and extensibility. The MkDocs nav is the
checklist: a shipped feature that isn't reachable from the nav is an incomplete feature.

## 16.5 Definition of done (documentation portion)

- [ ] Docs page created/updated under `docs/` in the correct category.
- [ ] Screenshot generated (visual features) via the screenshot test.
- [ ] Cross-links added to/from related pages; entry added to `mkdocs.yml` nav.
- [ ] `mkdocs build --strict` passes (no broken links/images).
